Two extensions edit what the model reads. In opposite directions.

memory adds. Once per turn it appends a block to the system prompt — an index, a set of facts, and the user's global file — so the session starts knowing things no transcript carries. context-diet subtracts. On every LLM call inside a turn it rewrites the message array bound for the provider, replacing old tool-result bodies with one-line stubs, so a turn that runs for hours never pays the over-window surcharge on output nobody is reading any more.

They never touch the same bytes: memory owns the system prompt, the diet owns the messages. But they share one cost model — the prompt cache invalidates from the first byte that differs — and that is what makes them one story rather than two.

hooks: before_agent_start · context memory budget 24,000 chars diet trigger 80% → 55% measured saving $107 → $52.71

01 · Shared spine

Anatomy of one request

Every call to the provider is one system prompt plus an array of messages. Each extension owns exactly one of those two, and neither can reach into the other's half.

02 · Shared spine

Where each one hooks

The difference in frequency is the whole design. memory fires once per turn, before the loop starts. The diet fires once per LLM call, inside it — which is the only place that can see a turn growing.

Why not just call compact()

ctx.compact() exists and can be called mid-turn. It opens with await this.abort(). Killing a 2.7-hour harness run to save tokens is not a trade worth making, so the diet trims what is sent and leaves the turn running.

03 · memory

The read path

Memory is per project, keyed by cwd. The first question every session asks is which directory on this machine holds this project's memory — and it is not always a store pi wrote.

  1. Resolve the source. piMemoryDir(cwd, piHome) is <XDG_CONFIG_HOME or ~/.config>/pi/memory/<slug>, where the slug replaces every non-alphanumeric character in the cwd with -. If that directory exists, it wins and the store is pi's own. Otherwise memory reads the inherited store: <inheritedHome>/projects/<slug>/memory.
  2. Probe for the foreign slug. pi's own path is written and read by one deterministic encoder, so it needs no probing. The inherited store's encoder is not pi's and has been observed to disagree with itself over underscores, so two candidates are tried — the plain one, and one that preserves _ — and whichever directory actually exists wins.
  3. Read the files. Every *.md in that directory, sorted. MEMORY.md is kept aside as the index; every other file is a fact, parsed for name, description and type out of its YAML frontmatter. The parse is deliberately lenient — the store has written both a flat type: and a nested metadata: block, and older files have no frontmatter at all — so anything unrecognised falls back to the filename and the raw body.
  4. Read the global file. A global user file, if one exists, is read where it lies. It is never cloned and never written: it is the user's, and it is not project memory.
  5. Assemble within the budget (next section), then hold the result until something changes it.
Nothing found

If there is no index, no facts and no global file, loadMemoryFor returns undefined and before_agent_start adds nothing at all. An empty memory costs zero tokens, not an empty heading.

04 · memory

Assembly and the budget

assemble() is pure, and it is where the shape of the injected block is decided. It fills a character budget in a fixed order, and what does not fit is dropped rather than truncated mid-fact.

Why the tool has a read action

Because assembly drops facts. A model asked to update a fact that was dropped for budget would otherwise rewrite it from memory of a file it never saw. memory(action:"read") is the escape hatch, and the tool description says to use it before rewriting anything.

05 · memory

The fork

pi does not edit a store it did not write. It reads one until the moment it has something of its own to say, and then it takes a copy. That is copy-on-write, and the copy is a fork, not a sync.

06 · memory

The write path

One tool, four actions. Two of them read, two of them mutate — and the mutating pair is the only place the fork can happen.

actionreads fromwhat it does
listresolved sourceNames every *.md, and says whether the store is pi's own or inherited.
readresolved sourceReturns one file whole. The escape hatch for a fact the budget dropped.
writepi's storeReplaces a whole file. Forks first if pi has no store yet.
deletepi's storeRemoves one file. A file that was not there is reported, not an error.

Three guards worth naming

  • The filename is model-supplied, so it is validated, not trusted. safeFileName takes one path component, markdown only: ^[A-Za-z0-9][A-Za-z0-9._-]*\.md$, no separators, no leading dot, no .. anywhere, 128 characters at most. ../../.ssh/config and notes.md/../../x both fail before any path is joined.
  • Enabled is re-checked at execute time, not only at registration. Settings reload on every session_start, and writing to a store that before_agent_start will never inject would report success for memory the model is not going to see.
  • Every write is temp-then-rename, the same as the clone and for the same reason: a reader must never see half a file. A trailing newline is added if the model did not write one.

What a write costs

After a successful write or delete, refresh() re-reads the store and re-assembles the block, so the next request carries the change. The tool says so in its result: "Memory now holds N fact(s) and is in your next request."

The cache bill

That next request has a different system prompt, and the system prompt is the first bytes of the cached prefix. So a memory write invalidates the entire cache for that call — the most expensive invalidation available in the whole request. It is the price of memory that is actually current, and it is why memory is a write-rarely store rather than a scratchpad. 

// the whole read-inject cycle, in the order it happens
session_start   → loadSettings() → resolveSource() → readMemory() → assemble()
before_agent_start → systemPrompt + "\n\n" + block        // once per turn
memory(write)   → ensureStore() [forks once] → writeFile() → refresh()
/memory         → status | show | reload

07 · memory

When it actually writes

Everything above is mechanism. This is policy — and the short version is that reading is automatic and unconditional, while writing is unguided: nothing in the extension ever asks for it.

Read is not a decision

Worth separating from the rest, because it is the half that cannot go wrong. The store is read and injected on every session, unconditionally. The read action is not how memory reaches the model — it is the escape hatch for the two cases the injected block cannot cover: a fact dropped for budget, and the file you are about to overwrite.

Write is judgement, and this is all of it

The entire policy lives in TOOL_DESCRIPTION in agent/extensions/memory/index.ts: 

Save what stays true and is not already recorded: how the user works, a decision and the
reason behind it, a project constraint that is not derivable from the code. Do not save
what the repository already says (structure, past fixes, git history), or anything
that only matters to this conversation.

Four types carry the same split — user, feedback, project, reference — and feedback and project are asked for a Why: and a How to apply: line, because a preference with no reason behind it cannot be applied to a case it does not literally name.

There is no update

write replaces a whole file. There is no append, no patch, no merge. "Updating a fact" is therefore read then write, and skipping the read silently truncates whatever the model did not remember. That is the reason the read action exists at all, and the reason the tool description says to use it.

actionwhat should trigger itwhat actually does
loadevery sessionpi does, at session_start. Automatic.
readbefore a rewrite; a dropped factThe tool description says so. Nothing checks.
writea durable fact the repo does not recordNothing. The model's own notice, or the user asking.
deletea fact that turned out wrong or staleNothing, and no criterion is written down either.
The gap, named by the repo itself

ask-user sits in the same agent/extensions/ directory and states the problem in its own header: "Offering the tool is not enough to get it used: the description, the snippet and the guidelines all sit in the cached prefix, read long before there is a request to apply them to."

Its answer is nudge.ts — an opening nudge on the turn that opens new work, and a second that watches tool_call for real cost being spent and speaks up after N distinct files have been mutated with no ask_user call in between. memory has the identical exposure and no equivalent. Its index.ts registers session_start, before_agent_start, the tool and /memory, and nothing else: no nudge, no reminder, no keyword, no end-of-session pass.

MEMORY.md is a convention, not a mechanism

The tool description asks for a one-line pointer in the index for every fact file. Nothing enforces it — readMemory loads every *.md as a fact whether the index mentions it or not, so an unindexed fact is still injected. The index only starts to matter once facts are being dropped for budget, which is precisely the moment the model can no longer see the fact it needs. A correct write is two tool calls, and the second one is the one that gets forgotten.

08 · memory

What a memory looks like

A store of 83 facts across 16 projects, read for this document. Two shapes account for all of them, and the second one answers a question the policy does not: yes, debugging insight is what memory is best at — but only the part of it that git cannot hold.

83fact files, across 16 projects
2shapes: short behavioural, long forensic
0written by pi — the store has never been created

That last number is the trigger gap from the previous section, measured rather than argued. Every one of the 83 was written by a different tool on this machine — one that nudges for it. pi's memory extension has been loaded the whole time, its tool offered on every turn, and it has never once written a fact — so the fork described in §05 has never happened.

Shape one — a behavioural fact

Short, about how the team works, and useless without its two closing lines. The Why is what lets the rule be applied to a case it does not literally name; the How to apply is what makes it actionable instead of a complaint on file. 

---
name: no-status-chips
description: "Team dislikes per-feature status-bar chips; do not add presence markers"
metadata:
  type: feedback
---

The team does not want features to paint status-bar "presence" chips. They
objected to each one on sight and had them removed.

**Why:** the status bar is limited space, and a static "this feature exists"
marker is noise, not information. It clutters without helping.

**How to apply:** the shared footer is now the central guard — it deliberately
does not render the per-feature status list, so no chip shows, present or future.
Do not re-add that loop. If a chip ever seems warranted it must carry live,
changing information, and be confirmed first. Related: [[footer-ownership]].

Shape two — a debugging memory

Long, specific, and organised around the wrong turn rather than the fix. This is the anonymised skeleton of a real one; everything structural is preserved. 

---
name: request-connection-fanout
description: "Random self-recovering \"failed query\" errors were per-request connection
              fan-out and unclosed clients, not query bugs"
metadata:
  type: project
---

Intermittent `failed query: select …` on the dashboard — random, self-recovering,
refresh-only, several unrelated queries failing together — was a CONNECTION
problem, NOT a SQL or schema error. The browser only ever showed `failed query`
because the SSR serializer drops the error `.cause`; the real messages, recovered
by walking the cause chain, were `network connection lost`, then `max clients`.

Two stacked causes:
1. Per-request fan-out. One page loader fired ~12 server functions, each
   opening its own client inside ONE request. The platform caps a worker at 6
   simultaneous outbound connections per request. Refresh-only, because a
   client-side navigation issues each function as its own request.
2. Clients were never closed, leaking until idle timeout and exhausting a
   pooler capped at 15.

**Fix:** one shared client per request via `withDb(fn)`, closed in a finally;
every query split into a `*Core(db, …)` plus a thin wrapper.

**Invariants — do not regress:** never open a client directly in a handler, use
`withDb`; never let one request open more than one client; never leave one
unclosed. Related: [[ssr-cpu-budget]].

The five parts, and why each one earns its tokens

The line worth proposing

The current tool description tells the model not to save "past fixes", and taken literally it forbids every example above. The corpus quietly ignores it, and is right to. The distinction that actually holds:

do not savesave
"Fixed the null check in the parser."→"Input from this vendor omits the field entirely; treat absent as zero, not as invalid."
"Refactored the loader into three functions."→"One request may open at most one DB client — the platform caps outbound connections at six."
"Bumped the dependency to 4.2."→"4.1 silently drops the error cause, which is why every failure here reads as the same generic message."
Anything a reviewer could read off the diff.→Anything that took an hour to find and leaves no trace once the fix is merged.
Proposed wording

A drop-in replacement for the "what to save" paragraph, widened to admit what the corpus already contains:

Save what stays true and is not already recorded: how the user works; a decision and the reason behind it; a constraint of the environment that the code does not state. After a hard debugging session, save the constraint you found and the invariant that prevents a repeat — not the fix, which is in the diff. Name the symptom it presented as, and the explanation you ruled out. Do not save what the repository already says, or anything that only matters to this conversation. If a fact you already hold turns out to be wrong, delete it; if it recurs in a new form, extend it rather than adding a second copy.

The index

MEMORY.md is one line per fact, and the hook after the dash is what a future session actually reads when the bodies have been dropped for budget: 

# Memory

- [No status chips](no-status-chips.md) — team dislikes per-feature presence markers; don't add them
- [Request connection fan-out](request-connection-fanout.md) — random "failed query" was connection
  fan-out, not SQL; one client per request
Two conventions, one corpus

Filenames in the store are split between feedback_*.md / project_*.md prefixes and plain kebab-case topic names, because the model picks the filename and nothing enforces a convention. Harmless for retrieval — the index and the frontmatter carry the type — but if this is being adopted by a team, pick one and put it in the tool description.

09 · context-diet

The gap it fills

One measured session, 019fcad1, is the entire argument. One prompt, one turn, and the compaction threshold that was supposed to prevent this was set correctly the whole time — it was simply never evaluated.

2h44mone turn · 399 model calls · 530 tool calls
375kpeak context, against a 272k window
219calls billed above the window
$125.86the session

The cost is not the compaction. It is the cliff: the gpt-5.6 family doubles every rate above 272k — input $5→$10 per Mtok, cached $0.50→$1.00, output $30→$45 — so those 219 calls turned into $81.85 of the $107 main-loop spend. The split is exactly clean: the largest 1× call carried 269,836 tokens, the smallest 2× call 273,729.

Compaction did eventually fire. First as overflow recovery, after the API had already returned "your input exceeds the context window"; then again at agent_end, 51 seconds after the final answer — 347k summarised and then never read. Together, $7.47, cache disabled by design, billed at the over-window rate.

Replayed through the diet

realwith the diet
peak context375k218k
calls above the cliff2190
main-loop cost$107.00$52.71

Five rounds across the session, 180 results stubbed, each round's cache break charged in full. Peak never reaches 255,616 either, so the overflow that forced the first compaction does not happen and the unread second one does not fire — the $7.47 goes with it.

Main session only

Workflow and task subagents spawn with --no-extensions, so the diet is not loaded there. They were never the problem: 270 subagent calls cost $5.35 between them, because each one starts empty.

10 · context-diet

A round

A round is rare on purpose. It fires at a high-water mark, trims well past it, and the gap between the two is the hysteresis that keeps the prompt cache stable in between.

How the current size is known

step() prefers ctx.getContextUsage()?.tokens — pi's own figure, anchored on the last usage the provider actually billed and extended with a local estimate for whatever arrived since. Once a round has run, that anchor is the trimmed size, so the number self-corrects on every response and never drifts against the real context. It is null only between a compaction and the next response; the local fallback used there reads low by the system prompt and the tool schemas, which is harmless at a point in the session nowhere near the threshold.

11 · context-diet

What gets dropped

Candidates are collected oldest-first, and a ladder of protections decides what is off limits. Two of the rungs reach inside the protected recent window, because they mark content that is stale now regardless of its age.

What the model sees instead

// an ordinary drop
[older output dropped to keep this session inside its context window — read(src/app.ts), 41.2 KB. Re-run the tool if you still need it.]

// a superseded read — pointed at the fresh copy instead of a pointless re-run
[stale copy dropped — read(src/app.ts), 41.2 KB. A newer read of this file appears later in the conversation.]

The label is the call and its arguments, clipped to 64 characters, indexed from the assistant message that made the call — so the stub names what the model asked for, not just the tool it used.

12 · context-diet

Stickiness, and the two invariants

Everything above describes one round. What makes the extension safe is what happens on the hundreds of calls that are not a round.

A dropped result is replaced, never removed

Delete the message and every later request is rejected for carrying a tool call with no result — which reads as a provider outage, not as a bug in an extension. The stub takes the message's place, keeping the call/result pairing intact.

A stub renders byte-identically forever

Evictions are permanent for the session and built from facts fixed when they were made. The prompt cache invalidates from the first byte that differs; a diet that re-decided each call would move that byte every call and re-bill the whole context uncached — ten times the cached rate, and strictly worse than doing nothing.

The consequence is in the last two lines of step(): once the eviction set is non-empty, every subsequent call gets the stubbed view — even if context later sits far below the target. The decision is not revisited, only extended. 

// session.ts, the tail of step()
if (evicted.size === 0 && reasoningDropped.size === 0) return {};   // nothing to do, leave the request alone
return { messages: applyDiet(messages, evicted, reasoningDropped), entry, escalation };

When the set is thrown away

A toolCallId only means something against one message list, so the whole diet resets whenever that list is replaced wholesale: session_start, session_before_switch, session_before_fork, session_before_tree, and session_compact. After a compaction the dropped results are gone from context outright and the summary that replaced them is small, so the counters and the pin set start over there too.

13 · context-diet

Reasoning, escalation, resets

dropOldReasoning — experimental, and on in this config

When enabled, a round also strips thinking blocks from all but the newest 10 assistant messages. The measured session carried 1MB of encrypted reasoning signatures across 455 messages — on the order of 10–25% of peak context, re-read on every call. Reasoning rides along on any round, and can carry a round alone when the results have nothing left to give: over the mark with every old body already stubbed, stripping reasoning is the only lever remaining.

Why it is off by default

The failure mode is a hard 400, not a quality dip. The OpenAI Responses API can reject a replayed function_call whose paired reasoning item is missing — "was provided without its required reasoning item" — and whether that check reaches long-completed rounds is undocumented.

This machine has contextDiet.dropOldReasoning: true in agent/settings.json, which is the documented validation plan: run it on real sessions, and if a turn dies with that error, turn it back off. Nothing else changes and the session is intact.

Escalation — the one time it breaks silence

A stub is deliberately silent, because it must render identically forever. That is fine for one round. It stops being fine when a turn re-reads its way through several: every stub ends with "re-run the tool if you still need it", which reads as permission to read straight back into a window that is about to fill up again. The measured session hit six rounds, roughly 100k tokens apiece, and never knew it — then hit the provider's own "input exceeds the context window" error, which is the failure highWaterRatio exists to pre-empt.

So past escalateAfterRounds rounds in one turn, once and only once, the model is told directly and an attended user gets the same news as a ctx.ui.notify warning rather than a muted transcript line.

steer, not followUp

followUp only drains once the model stops calling tools on its own — which is exactly the behaviour this reminder exists to interrupt, so a runaway turn would never see it. steer is polled every round, right after the current round's tool results and before the next LLM call: the earliest the model can act on it, and where the round that triggered it just landed.

The transcript line

Every round appends a custom entry — not a message, so it costs no context — recording how many results were dropped, the tokens before and after, and how many reasoning blocks went with them.

14 · Together

Where they meet

They never edit the same bytes, but they are coupled twice: through the cache, and through the threshold.

  1. Memory is a floor the diet cannot lower. The diet rewrites messages; the memory block lives in the system prompt. So the block is a fixed cost on every call of every turn, and no round can trim a byte of it. At the default 24,000-character budget that is roughly 6k tokens standing on every request. If context is tight, the lever is memory.maxChars or memory.includeFacts — never the diet.
  2. Memory makes rounds fire sooner. The diet's trigger is measured against getContextUsage(), which counts the whole request — system prompt included. A larger memory block therefore reaches the 80% mark earlier and buys fewer messages of headroom before the first round.
  3. Both are cache events, at opposite ends of the prefix. A memory write invalidates from byte zero, the worst possible position. A diet round invalidates from its oldest eviction, which is deliberately far along and deliberately infrequent. Neither is free, and both are designed to happen rarely for the same reason.
  4. Their lifetimes are opposites. Memory is the thing that survives the session and is meant to be re-read next week. The diet's eviction set is thrown away the moment the message list is replaced — a new session, a fork, a compaction — because a toolCallId means nothing outside the branch it was made on.

15 · Together

Sharp edges

Four things that are true of the code as it stands, and are not obvious from reading either extension's header comment.

A global user file that does not fit is dropped silently

assemble() adds the global block first and ignores whether it fit. The index and the facts both set the truncated flag when they overflow, and that flag is what appends the "some memory was omitted" line and what /memory reports. The global block sets nothing — so a a global file larger than memory.maxChars vanishes with no note anywhere.

The pin channel has no publisher

context-diet:pin was built for the visual-reference extension — a reference mockup that must outlive the agent's own newer screenshots. That extension was removed in 898261e, and nothing else emits on the channel. The consumer, the cap and the protection rung are all still there and all currently unreachable. Harmless: the set defaults to empty.

Once anything is evicted, the view is always rewritten

Not a bug — it is the byte-identical invariant doing its job — but worth knowing when reading a transcript: after the first round, no call in that session sends the original bodies again, however far context later falls.

dropOldReasoning is on here

The experimental flag, whose documented failure is a hard 400 from the Responses API rather than a quality dip. That is the deliberate validation plan, but it is a live setting on this machine and the symptom to watch for is specific: "was provided without its required reasoning item".
