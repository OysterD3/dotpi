Set a condition. The agent is not allowed to stop until it holds.

/goal all tests pass and the linter is clean. From then on, every time the agent tries to end a run, a separate tool-less LLM call reads the transcript and judges it against the condition. Met, and the goal clears itself and prints what it cost. Not met, and the reason is fed back and the agent resumes.

The interesting part is that pi has no stop hook — no event whose return value can veto the end of a run. Everything below is what that constraint does to the design.

judged on agent_end resumed by a follow-up transcript budget 50% of the judge's window cap 20 iterations

01 · The mechanism

The shape it wants to be

The natural design is a session-scoped stop hook: the agent tries to stop, a handler judges the work, and either lets it stop or blocks with a reason. pi has no such hook, and neither agent_end nor agent_settled reads its handler's return value. So the block is expressed the way pi's own shipped example does it — and the observable behaviour is identical.

What a stop hook would do

  • Agent signals it is finished.
  • Hook judges, returns {block: true, reason}.
  • The runtime declines to stop and hands the reason back.

What this does instead

  • Agent finishes; agent_end fires.
  • The handler judges, and on "not met" sends a follow-up message.
  • A delivered message resumes the agent. Same loop, pi-native.
The one thing the substitution costs

A blocked stop would resume by definition. A follow-up message does not — it is just text arriving. So the message has to say the quiet part out loud, and notMetInstruction does: "The goal is not met yet. Continue working toward it. Do not stop to ask the user what to do next." Without that last sentence the agent reads a critique and asks what you would like to do about it.

03 · The mechanism

The judge

The right way to constrain a judge is a provider-level JSON schema. pi's stream options have no equivalent, so the schema is enforced by hand: the prompt demands bare JSON, the response is scanned for the first balanced brace run, and the result is validated. Anything that fails validation is an error, never a silent "met". 

// the three shapes the evaluator may return
{"ok": true,  "reason": "<quote evidence from the transcript that satisfies the condition>"}
{"ok": false, "reason": "<quote what is missing or what blocks the condition>"}
{"ok": false, "impossible": true, "reason": "<why it can never be satisfied>"}

Models wrap JSON in prose or fences even when told not to, so extractJson scans for the first balanced brace run rather than trusting the whole string — tracking string literals, so a brace inside a quoted reason cannot end the scan early.

The read order is load-bearing

A provider rejection is not an exception here. completeSimple resolves with an assistant message carrying stopReason: "error" and the provider's text in errorMessage; only transport-level failures throw. So every outcome is read off the resolved value — and the order it is read in changes what the feature does.

04 · The mechanism

Five verdicts

verdictthe goalwhat happens
metclearsAn outcome entry is appended with the duration, the turn count and the tokens spent. Display-only — it never enters context.
impossibleclearsThe loop ends rather than retrying forever. Deliberately hard to reach: the judge is told to confirm independently and, when in doubt, to return a plain not-met.
not_metstaysIteration count up, reason recorded, follow-up sent, agent resumes.
errorstaysWarns, does not block, does not count as an iteration.
abortedstaysSilent. An interrupt is not a failed check, and the next stop attempt evaluates again.
Two races, both closed

The judge call takes tens of seconds and you can type through it. If you cleared the goal or set a different one meanwhile, the verdict answers a question nobody is asking — so before acting on it the handler re-checks that the goal object is still the same one. Without that, /goal clear could fail to stop the loop, or the old goal's reason could be fed back under the new goal's name.

And agent_end can fire again while the first evaluation is in flight, so a latch makes the second one a no-op rather than a second call and a duplicate follow-up.

05 · The mechanism

What the judge reads

The evaluator is tool-less, so the conversation has to arrive as flat text. Tool calls are included, and that is the point: "did you run the tests" is answered by a tool call, not by prose.

  • Budget: half the evaluator model's context window, oldest sections dropped first — evidence that a goal was met is recent.
  • When anything was dropped, a notice says so and tells the judge what to do about it: if the required evidence may be in the omitted prefix, return insufficient evidence in transcript rather than guessing.
  • An empty transcript is a not-met, with that same reason — never an error, and never a pass.
The limit worth understanding before you rely on it

The judge grades the conversation, not the world. It has no tools, no repo and no shell — its only evidence is what the transcript contains. A condition like "all tests pass" is satisfied by transcript evidence that tests were run and passed; an agent that merely claims they pass produces the same words. The prompt pushes back hard — quote evidence, and return insufficient-evidence when there is none — but the failure mode is inherent to judging a transcript, and it is why conditions that name an artefact ("the test command exits 0 and its output is in the transcript") hold up better than conditions that name a feeling ("the code is clean").

06 · Staying alive

Surviving the session

A goal outlives the process, so it is written to the session as a custom entry — and custom entries do not enter LLM context. That is exactly what you want for bookkeeping, and exactly what creates the next problem: after a /resume, the goal is active and the model has never heard of it.

Time is banked, not measured

setAt alone would count wall-clock across a resume, so a goal set before dinner reports "16h" the next morning beside a turn count and a token figure that both measure work. Elapsed time is banked at each persist and the clock restarts for the new session — losing only the stretch between the last write and the process exiting.

The token figure is dropped rather than faked in the one case it cannot be known: a compaction mid-goal leaves the current context reading below the baseline, and printing "0 tokens" would claim the goal was free.

07 · Staying alive

autoCapture

A benchmark traced a runaway session to this extension sitting unused: a request with explicit acceptance criteria ran to a bad result with nothing checking it against them, because nobody had typed /goal. goal.autoCapture closes that — off by default, because a stop-gate nobody asked for is a tax on every reply.

08 · Living with it

What it costs

Every stop attempt while a goal is active costs one extra LLM call carrying up to half the context window. That is inherent to the design — there is no way to judge a transcript without reading it.

goal.model is how you make it cheap

Judging is a single yes/no read that runs on every stop attempt, so it is worth doing on a small fast model rather than the session's frontier one. pi has no small-model concept to inherit, so this names one explicitly. Unset, the session model judges its own work — which is both expensive and the least independent option available.

maxIterations is how you bound it

20 by default. A runaway loop spends real money unattended, so the cap is finite unless you say otherwise; 0 lets a goal run until you interrupt it. Note it counts over the goal's whole life, not as a consecutive run — nothing resets it.

The spend is announced on the same usage:spend channel every billing extension uses, so judge calls show up in /usage instead of being money nothing can see. Every branch is announced, including the aborted and errored ones — they were billed too.

A typo is caught at load, not at the first stop

If goal.model names nothing resolvable, the warning fires when the session starts and when the goal is set — not on the first stop attempt. Left to evaluation time, a typo would turn every stop into a failed check: the goal would never block, never cap and never clear, and the only signal would arrive once per stop, long after the file was edited. Credentials still cannot be checked without an async call, so an auth failure remains an evaluation-time error.

09 · Living with it

Sharp edges

A broken evaluator makes a goal that never ends

An error verdict does not block, does not clear, and does not count as an iteration — so it cannot reach the cap either. A goal whose evaluator fails every time therefore stays active indefinitely, across resumes, costing one failed call per stop attempt and warning each time. That is the correct behaviour for a transient failure and an awkward one for a permanent one; the warning is the only signal.

The cap counts a lifetime, not a streak

Twenty not-met verdicts end the goal however they were spread out — including across resumes, since the count is persisted. A long-lived goal that made real progress between misses is capped on the same arithmetic as one that never moved.

It grades the transcript, not the repo

No tools, no shell, no filesystem. Conditions that name observable artefacts in the conversation hold up; conditions that name a state of the world depend on the agent having put evidence of that state into the transcript.

autoCapture spends its shot on a miss

By design, but worth knowing: if the first substantial message of a session is a question rather than a request, the extraction call runs, returns null, and the session gets no further attempts even when the real request arrives two messages later.

10 · Reference

Settings

Under a top-level goal key in ~/.pi/agent/settings.json, or <project>/.pi/settings.json when the project is trusted. 

{
  "goal": {
    "model": "<provider>/<small-fast-model>",  // unset = the session model judges itself
    "maxIterations": 20,                       // 0 = no cap
    "autoCapture": false                       // opt-in
  }
}
keydefaultnotes
modelunsetNames an already-registered model, so a project cannot register a provider or supply a key through this block. Warned about at load if unresolvable.
maxIterations20Whole number ≥ 0, validated as an integer on purpose: flooring 0.5 would turn the tightest cap anyone could ask for into "no cap at all".
autoCapturefalseThe one setting that changes behaviour and spend with no explicit command, which is why it is opt-in and why an untrusted project cannot switch it on.

Project trust

Project settings are honoured only when the project is trusted, and when they are ignored every dropped key is named — reporting only model once left a project's maxIterations silently ignored, so a cap the repo asked for looked like a cap the user chose.
