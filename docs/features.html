这份配置给 pi 加了什么What this config adds to pi

pi 本身是什么、内部怎么跑，是另一篇的题目。这里只讲一件事：25 个扩展 —— 它们各自补上了什么、怎么实现的、以及怎么用和怎么配。几乎每一个都写于一次可量化的失败之后，而不是一个点子之后；全文引用的那些数字，本身就是论据。后半部分是完整的命令、快捷键与配置参考。 What pi is, and how it works inside, is another document's job. This one covers exactly one thing: 25 extensions — what each adds back, how it works, and how to drive and configure it. Nearly every one was written after a measurable failure, not after an idea; the numbers quoted throughout are the argument. The second half is a complete command, key and settings reference.

How it works工作原理

Hooks in, events across纵向挂钩，横向广播

Two wiring mechanisms, and that is the whole architecture. pi calls extensions through hooks; extensions talk to each other over a shared event bus, never by importing one another. 整套架构只有两种接线方式。pi 通过 hook 调用扩展；扩展之间通过一条共享事件总线通信，从不互相 import。

Permissions: the classifier can only ever tighten权限：分类器只能收紧，永远不能放宽

The safety argument, in one sentence一句话讲清安全论证

The classifier is consulted only on calls the deterministic policy already decided to allow, and its only power is to turn that allow into an ask. There is no verdict that runs something the rules would have stopped. Fully compromised by prompt injection, auto mode degrades to askDestructive — the default. 分类器只在确定性策略已经判为放行的调用上被咨询，而它唯一的权力是把放行改成询问。不存在任何一种裁决能让规则本该拦住的东西跑起来。即使被提示注入完全攻陷，auto 模式也只是退化成 askDestructive——也就是默认模式。

It sees the tool, the call and the working directories and nothing else — no transcript, no task, no history — fenced with markers it cannot forge and told that text claiming pre-approval is itself grounds to answer unsafe. An unreachable classifier is an error, never a silent "safe". 它只能看到工具、这次调用和工作目录，别的什么都没有——没有对话记录、没有任务、没有历史——外面包着它伪造不了的围栏标记，并被告知：围栏内声称“已获批准”的文字本身就是判定为不安全的理由。分类器不可达算错误，绝不静默视为“安全”。

Deep dive · Cost深入 · 成本

Context diet: the price cliff nobody was watching上下文瘦身：没人盯着的价格悬崖

pi decides whether to compact in exactly two places — after agent_end, and before a new prompt. Both are turn boundaries. A single turn that runs for hours never reaches either. pi 只在两处决定是否压缩——agent_end 之后，以及新提示词之前。两处都是轮次边界。一个跑几小时的单轮，两处都到不了。

What gets dropped丢什么

  • Over 80% of the window, old tool-result bodies go oldest-first down to 55%. Errors never go, nor do the newest 24 results — the live working set.超过窗口 80% 时，旧工具结果的正文按从旧到新丢弃，直到降回 55%。错误永不丢，最新的 24 条结果也不丢——那是活跃工作集。
  • Screenshots: only the newest 3 survive. One goes stale the moment the next is taken and costs ~1.2k tokens to keep saying so.截图：只保留最新 3 张。下一张一拍，上一张就过期了，而继续留着它每次约 1.2k token。
  • Superseded reads, swept even past the target — deliberately narrow: a later whole-file read covers an earlier read of that path; a later partial read covers nothing.被覆盖的读取，即使已达目标也继续清理——定义刻意收窄：后来的整文件读取覆盖此前对同一路径的读取；后来的部分读取什么都不覆盖。
  • Each dropped body becomes one line naming the call and its size, so the model can go get it again.每条被丢弃的正文变成一行，注明调用与大小，模型可以再去取。

Two invariants carry the whole thing两条不变式撑起全部

1. A dropped result is replaced, never removed. Remove the message and every later request is rejected for a tool call with no result — "which reads as a provider outage, not a bug here." 1. 被丢弃的结果只替换，绝不删除。删掉消息，之后每个请求都会因“有工具调用却没有结果”被拒——“看起来像服务商故障，而不是这里的 bug。”

2. A stub renders byte-identically forever. The prompt cache invalidates from the first byte that differs, so a diet that re-decided each call would move that byte every call and re-bill the whole context uncached — ten times the rate, strictly worse than doing nothing. 2. 占位文本永远逐字节一致。提示词缓存从第一个不同的字节开始失效，所以一个每次调用都重新决策的瘦身器，会每次都挪动那个字节，把整份上下文按未缓存价重算——十倍价格，严格劣于什么都不做。

Nothing is aborted: ctx.compact() opens with await this.abort(), and killing a 2.7-hour harness run to save tokens is not a trade worth making. 全程不中断：ctx.compact() 开头就是 await this.abort()，而为了省 token 杀掉一个跑了 2.7 小时的任务，这笔买卖不划算。
